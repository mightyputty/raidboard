How one codebase serves both

The only thing that differs between the hosted site and the download is where log lines come from. Everything above that line — scoring, map plans, guides, story chapters — is byte-identical.

Hosted · raidboard.gg

Browser reads the Logs folder through a directory handle. Chromium only. Reads while the tab is open.

Download · raidboard.exe

Local watcher polls every 2s in the background. Any browser, no permission prompt, caches screenshots for offline use.

Neither

Firefox, or someone who declines. Falls back to ticking by hand, like every other tracker.

all three feed the same interface
Shared core

Quest journal, map scoring, per-map loadouts, pins, story chapters, wiki guides. Progress in localStorage, with export and import for backup.

The six stages

Ordered by dependency, not by appeal. Each unblocks the next, and the piece most likely to fail outright sits early on purpose.

  1. 1

    Strip, rename, open the repo

    about half a day Everything downstream is smaller once the dead code is gone

    Cutting the two features you dropped removes a mode toggle, a filter, two chip styles and a branch through every scoping function. Do it before anything else, so the restructure and the log port work on the smaller surface.

    • Delete the mode toggle, the Kappa chips and filters, and the k field from the dataset.
    • Keep req, the unlock chain. Marking a quest done still cascades to its prerequisites and the Quests page still separates locked from available. Drop the visible chain caveat — that is a note to you, not to a stranger.
    • Rename to Raid Board throughout, and register raidboard.gg.
    • MIT licence, a README written for players rather than for you, CONTRIBUTING, and attribution for tarkov.dev and the wiki under CC BY-SA.
    • GitHub repo with Cloudflare Pages connected, deploying the current build as-is so the pipeline is proven before it matters.
  2. 2

    Split the payload, add PVE

    about 2 days Guides for 517 quests have nowhere to live until this lands

    One inlined 651 KB HTML file works today and stops working the moment every quest carries a guide. It becomes a small shell, a core dataset, and one lazily-fetched file per quest.

    • index.html — shell and app only, roughly 60 KB.
    • core.json — quests, objectives, maps, keys, scoring. Everything needed before you click anything.
    • One guide file per quest, fetched only when a Guide button is pressed.
    • PVE is far cheaper than I first estimated: 517 PVP tasks against 514 PVE, only 26 and 23 exclusive either way, and every shared quest has identical objectives. So it is one list of about 540 quests tagged pvp, pve or both — roughly 5% more data, not double.
    • Nightly rebuild in GitHub Actions that commits the built data, so an outage upstream never takes the site down with it.
  3. 3

    Move the log reader into the browser

    about 3 days Riskiest piece — prove it before building on it

    The whole hosted product rests on this working. Chrome 151 on your machine has every API it needs and the proof-of-concept parses your real logs, so the remaining risk is whether the permission survives between visits, not whether the reading works.

    • Port lib/logs.js to run in the page. The parsing is unchanged; only file access differs.
    • A log-source interface with three implementations: local watcher, directory handle, none.
    • Directory handle kept in IndexedDB so the folder is chosen once, ever, with one click to re-grant if the permission lapses.
    • Detect the mode from Session mode: PvpSeason and switch the quest list to match.
    • Fix the failed-quest bug while you are in here. Message type 11 means failed and nothing reads it, so Chemical Part 4 and Big Customer still show as active on your board. The text field lies — it says quest started even on failures, and only the failMessageText suffix is honest.
    • A first-run flow, because there is none today — it works because it is your machine.
  4. 4

    Guides for all 517 quests

    about 3 days The wedge — the reason to use this over TarkovTracker

    The machinery exists and is proven on the story chapters: a guide-section parser, exact-then-fuzzy heading matching, and item location pages found through links and backlinks. This points it at every quest in the game.

    • Wikitext for all 517 pages costs about 11 requests, not 517 — the API takes 50 titles at a time.
    • Reuse the story parser unchanged. Sections matching no objective keep going to Also in the guide rather than being attached to the wrong step.
    • Item pages via links and backlinks, kept only when the Location section has a gallery. Without pictures it is always a generic loot list and no use to anyone.
    • The hosted build points images at the wiki CDN; the download keeps caching them to disk so it works offline.
    • Expect real gaps. The wiki writes no guide for plenty of objectives, and that has to read as nothing written for this one rather than as a broken feature.
  5. 5

    Package the download

    about 1 day Independent of the site, so it can slip without blocking launch
    • Node’s single-executable build, bundling the watcher and the static site into one file. Double-click, the browser opens, done.
    • No Node install and no terminal. That matters: most Tarkov players are never going to run a command to start a quest tracker.
    • Unsigned binaries trip SmartScreen. Either document it plainly with a checksum, or budget roughly 200 dollars a year to sign. Documenting is fine to start.
    • Ship from GitHub Releases so the binary and the nightly data rebuild stay in step.
  6. 6

    Make it survivable

    about 2 days Last, because it hardens what the other five built
    • Wipe day: log-driven tracking heals itself, since a wipe resets the logs too. Only hand-set marks need clearing, so detect the profile change and offer it rather than doing it silently.
    • Degrade properly when upstream is down. tarkov.dev’s GraphQL has been returning 422 this entire time, so the site must never depend on a live third party at page load.
    • A landing page that says what it does in one line, and a privacy note that can afford to be blunt: there is no server to send anything to.
    • Say plainly that logs are read and never written, and that nothing is injected into the game. People will ask, and TarkovMonitor set the precedent.

What the logs can and cannot tell us

Checked against your 29 session folders rather than assumed, because each of these either removes a setting or kills a feature idea.

What could go wrong

tarkov.dev is a single point of failure

Their GraphQL API has been down the entire time this was built, and the whole dataset comes from their static dumps. Commit built data to the repo so the site serves the last good copy indefinitely, and treat a failed rebuild as a warning rather than a deploy.

Wipe day is launch day and breaking day at once

It is when every player goes looking for a tracker and when all the quest data churns. Traffic is free on a static host, so the risk is correctness, not load. Have a rebuild you can run on demand rather than waiting for the nightly job.

Fandom could block hotlinked images

Thousands of screenshots served from their CDN to strangers is exactly the pattern hosts block. The fallback is Cloudflare R2, which costs money and brings attribution duties, so keep the build able to switch image hosts with one flag.

Auto-tracking is Chromium-only on the web

Firefox has declined to implement directory picking. Tarkov is Windows-only so the audience skews heavily to Chrome and Edge, but roughly 5 to 7 percent land on manual ticking. The download has no such limit, which is a real reason to offer it.

SmartScreen will flag the executable

An unsigned binary that reads game files is exactly what a wary player is right to hesitate over. Publish checksums, keep the source open so the build is reproducible, and revisit signing if the download gets traction.

The domain becomes permanent

Progress lives in localStorage, which is scoped to the origin. Moving off raidboard.gg later wipes everyone’s hand-set ticks unless they export first. Worth making export prominent from day one regardless.

Before stage 1

Two things worth doing first, both cheap.

Confirm the proof-of-concept. It is still running on 127.0.0.1:8779. Point it at your Logs folder and check the counts match the board. If they do, stage 3 is derisked before a line of it is written — and if the permission survives a reload without prompting again, so is the returning-visitor experience.

Register raidboard.gg. It was free as of this writing, but that is not a reservation, and every document from here on names it.
